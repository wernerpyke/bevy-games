# Roadmap

Items that are done are in [ROADMAP-completed.md](ROADMAP-completed.md).

## Items for Future Implementation

Each item has a stable ID (`rm<n>`) that is assigned once and never reused or renumbered, the same rule as an ADR ID (`dev-docs/adr/WORKSPACE.md` adr-w8). Other documents refer to an item by its ID. The priority is the number in the heading, and the items are listed in priority order (the lowest number is next). To re-prioritise, change the priority number and move the item. Never change the ID.

### rm1. Art pipeline (priority 1)

Finish the art pipeline for Long Way. Done: the palette is chosen and grows by appending colours (`adr-a4`, `adr-a5`, `adr-a8`, `adr-a10`, 56 colours); the map cell is 64 px and art is drawn at 1x or at a whole-number scale; the player is the Hunter, built from a sprite pack with `tagged_sheets.lua`, `extend_palette.lua` and `resize.lua` (`adr-lw15`, `games/long-way/docs/HUNTER-sprites.md`). Existing assets in `~/Dark/graveyard_shift/diodrama-assets/` are still copied one file at a time on request (`adr-a3`). `Guy.aseprite` is still in `assets/art/characters/` but no code uses it.

Remaining: decide whether the sprite sizes need one grid rule (now: Hunter 128x128 at 1x, trees 128x128, rocks 32x32 at 4x); write the shared helper `dev-scripts/aseprite/lib.lua` from `art-pipeline.md` rule 1 (not written, the scripts are standalone); draw real `Up` and `Down` walk frames and an idle for each direction (placeholders from the pack jump frames now); decide whether to draw or drop the `Block` tag; wire up the `Hurt` and `Die` tags (no code plays them); and, when attacks come, add the attack, charge, special and dash sheets and split the baked-in effects into separate sprites. Decide whether to delete `Guy.aseprite`.

### rm2. Evaluate avian2d (priority 2)

Spike `avian2d` 0.8.0 (declares `bevy ^0.20`) in a separate game under `games/` and compare it with the custom collision in `adr-lw1`. Questions to answer: whether the 50% overlap from below and the walk-behind-from-above rules can be expressed with sensors or collision filters, wasm build size and build time against the current baseline, behaviour with real-time top-down movement and later NPCs (`adr-lw7`), and how testable the result is without a running world. ### rm3. Robust map and collision pipeline (priority 3)

R-Town and Long Way reload their map from disk on F1 on native (`adr-rt8`, the key is in the kit, `reload.rs`); the web build does not. The kit now has an occupancy grid and A* path finding built from the collision outlines (`adr-x23`), which covers the first part of the navigation idea below. The maps use `include_str!` and an own parser for the front matter and the drawn grid (`adr-lw8`, `adr-x18`). For a real-time RPG with many areas, plan a sturdier approach. Considerations: a Bevy asset loader with hot reload (edit a map and see it without a rebuild, also on the web build); a real YAML parser or Tiled maps (`bevy_ecs_tiled`) instead of the own subset; validation with clear errors; one map file per area with chunked collision; dynamic obstacles (doors, destroyed objects) that rebuild one cluster; a broad phase for many moving entities; and a navigation mesh or occupancy grid for NPC pathfinding built from the same outline. Decide when the second map or the first NPC appears. Update 2026-11-06: the second map is here. Long Way has three maps joined by exits and entries, a registry with a link check, and scene transitions (`adr-x30`, `adr-x31`). The registry keeps our own parser and `include_str!`; the asset loader question stays open.

### rm4. Map data beyond one grid (priority 4)

Maps are text files with front matter and one drawn grid, one character per cell (`dev-docs/extensions/map-files.md`, `games/long-way/docs/maps.md`, `adr-x18`). This suits maps that a human reads and edits as a picture. Maps may become more complex than one object per cell handles well: several layers (ground and objects), objects with their own settings, areas with triggers or dialogue, enemies and paths, and values that need real types (numbers, lists, nested data). Options: more grids in the same file (a `layer:` name per grid), a companion YAML or TOML file for data, chunk files for large maps, and generated maps (a seeded generator, with a per-chunk seed from the master seed and the chunk position, can return the same `Map` as the parser). Questions to answer: how layers and larger objects look in the grid, whether the human editing experience stays as good, error messages with line numbers, wasm support of any parser crate (check each crate for the pinned Rust and Bevy), and how it fits with `rm3` (asset loader, hot reload, Tiled maps). Not worth doing now. Decide when a map needs data that one grid handles badly. Keep the parser in `map.rs` behind one function (`parse`) so the format can change without touching the code that spawns objects. Update 2026-11-06: the front matter now has two more nested blocks, `exits:` and `entries:` (`adr-x30`), read by the same parser. They show the pattern for map data that is not one object per cell. Moving between maps is in `dev-docs/extensions/map-transitions.md`.

### rm5. Tiled backgrounds (priority 5)

Update 2026-11-08: a decorative first step exists, a colour and random tile images per map (`adr-x36`, "Map backgrounds (random fill)" below). This item is still open for a real tile layer with blocking tiles.

Give maps a ground made of tiles, so R-Town can draw grass, paths, stone and water instead of one flat colour (the placeholder `GROUND_COLOR` in `games/r-town/src/map.rs`). The pack's `0-tileset.png` (320x192, a 16 px grid of 20x12 tiles) is the first source. Considerations: how a map file describes a tile layer (a new section in the markdown format, or an external editor format such as Tiled, which ties in with `rm6`); whether a maintained crate fits the pinned Bevy version and wasm (for example `bevy_ecs_tilemap`, to be checked before any decision) or custom code, with the chunked drawing that a 60x60 map needs; where tiles sit in the draw order (`BACKGROUND_Z` and its sublayers in the kit layers); how blocking tiles such as water feed `CollisionWorld` (`adr-rt5`: water blocks the player), merged into the same clusters as objects; packing the terrain tiles into an `.aseprite` file with tags (`adr-rt1`, `adr-rt6`); and whether the kit or the game owns the tile layer.

### rm6. Visual map editor (priority 6)

Goal: edit a map by clicking cells and save the result in the text map format (`dev-docs/extensions/map-files.md`, `adr-x18`). The text file stays the source of truth, so editing by hand keeps working. Build it later, after the map format settles (`rm3` and `rm4`).

Considerations. The editor reads and writes the same files as the game, and a round trip must not change a file the user did not edit. It keeps comments, rulers, row labels, blank footprint cells and the front matter as written. The parser in `game-kit` (`parse`) does not keep these, so the editor needs a writer that edits the text in place, or a parser that returns the layout with the objects. Options: an in-game editor on top of the F3 grid and the debug tools (Bevy, native and web, no new language, and it draws the real art and footprints); or a separate tool. The language rule applies: Rust, Lua and shell only, and any other language needs approval. Features to consider: pick a kind from the legend and paint or erase cells, undo, a live footprint outline, the player start marker, a size change that adds or removes rows and columns, errors from `parse` shown in the editor, and a save that keeps `origin` (`bottom-left` or `top-left`) and the row labels right. Research on existing editors (Tiled, LDtk, Ogmo and the plain text editors for ASCII maps) was done when the format was chosen. Those need their own UI and formats, so they are not a fit for now.

Known issues. The file has no footprint data, so the editor needs the sizes from the game (`Kind` and its art) to draw footprints. Layers and objects bigger than one cell were left out of the format on purpose, and an editor may bring them back (`rm4`). Seeded generated maps (`rm4`) would need a way to save a generated result and then edit it as a normal map.

### rm7. Groups: tune by playing, then mixed footprint sizes (priority 7)

Goal: a planting of trees, shrubs and rocks of different sizes becomes one solid shape where the player sees one, stays passable where the player sees a gap, and the developer can tell why. Today every kind has a rectangular footprint (`Kind::footprint`), and objects are grouped when their footprints overlap or touch, also at a corner (`adr-lw14`, `adr-lw23`). A member of a group blocks its anchor cell (a tree: its trunk cell, `adr-lw18`) and a lone object blocks a thin band (`adr-x20`, `adr-rt9`). This is simple, and it has two weak points that showed up when the Zen Garden trees and shrubs were added: the canopy counts as much as the trunk, and the rule is invisible.

Steps, in the order we suggest:

1. Show groups in the debug tools: draw each footprint, colour it by group and print the group size, and let the scripted run print the groups of a map. This costs little, and it makes every later step easier to judge.
2. Check by playing whether the current rules feel right and whether the area per member should change. Questions: a thinner footprint for tall trees so the player can walk closer behind a grove; a deliberate gap size; and the Long Way top inset that is dropped when a member sits above (`Group::neighbour_above`). Known issue: a lone rock in Long Way has a 12.8 px band, which the developer has not yet tried in play.
3. Give each kind a solid shape apart from its footprint: the cells that hold the trunk or base (the medium green tree has its trunk in its left cell, `green_tree` in its right cell). Group on the solid cells and keep the footprint for placement and sorting. Then a canopy corner touching a shrub no longer makes a wall. Preferably the art file says it, as a named Aseprite slice such as `solid` next to the footprint, so the art stays the source of truth as for animation speed (`adr-a6`). Check that `bevy_aseprite_ultra` reads slices before choosing. Otherwise keep a table per kind in code (today: `Kind::footprint` and the `art` table in `scenery.rs`).
4. Decide by gap width, not by cell adjacency: the player is 28 px wide, so two blocked boxes closer than that already merge in the outline. A rule that closes only gaps the player cannot fit through would make a grove feel the same as it looks. A solid hedge or wall would still need its own kind or a legend parameter, so a developer can ask for a solid line on purpose and not by a lucky layout.
5. Corner contact: keep it for solid cells, because two cells that touch only at a corner leave no gap the player can use. Drop it for canopy cells. Today a single diagonal neighbour turns a passable tree into a solid one.
6. The visual map editor (`rm6`) should show footprints, solid cells and groups, so a developer sees the effect of a placement while drawing.

Known issues: a shrub placed diagonally next to the empty canopy cell of a medium green tree (`1.txt`, col 6 row 1) becomes a full-cell block, as the rule says (`adr-lw23`). The kit groups items of one size only, so the game expands footprints into cells before calling it. A per-item footprint in `game_kit::groups` would be cleaner, and R-Town would have to follow.

### rm8. Keyboard and mouse input in the game-kit (priority 8)

Started: the kit turns a mouse click into a world position (`pointer.rs`, `WorldClick`, `adr-x42`), and the Long Way player walks by clicking (see "Click to move (Long Way)" in `ROADMAP-completed.md`). Still open: R-Town's game-local `PlayerInput` resource (move direction, fire) filled from the keyboard (`adr-x22`) should move to the kit, so that no game code reads `KeyCode` or mouse buttons directly. Considerations: keyboard and mouse as two sources that write the same resource, with the last used device winning; mouse aim for R-Town converted through the pixel camera (`pointer::cursor_to_world` already does the conversion) and an aim direction that can replace the facing direction; named actions with default key bindings that a game can override, and later rebinding and gamepads; the scripted run tool (`script.rs`) writes key presses into `ButtonInput` and sends `click:` as a message; touch taps on the web are not handled (a first touch could send `WorldClick`); hold-to-follow was not built (Long Way is click to go only, `adr-lw30`); wasm differences (pointer lock, touch). Keep game specific actions out of the kit, as for the other modules (`adr-x12`).

### rm9. Combat basics (priority 9)

The player can pick a weapon in a drawer that slides up from an energy icon (`adr-lw31`, `weapon_menu.rs`): it sends `WeaponChosen` and nothing reads it yet. The weapons themselves are planned in `PLAN-weapons.md`. Projectiles and enemies exist (`### Enemies (R-Town)` and `### Ghost enemy and player HP (Long Way)` in `ROADMAP-completed.md`). The player has 3 HP in Long Way, but R-Town has none, and there is no way to kill a ghost yet (a weapon in Long Way is the next step). When several enemies attack at once, revisit the hit timing: the hit lands when the ghost's `Attack` ends. Considerations: hit points and damage, an impact effect and sound, a death screen and a restart flow with a game state (`States`), enemy attacks, weapon values in one place (speed, cooldown, range, damage) and more than one weapon, and exact blocked shapes for projectiles if the 5 px early stop at tree sides is a problem (`adr-x21`). Decide when the first enemy is designed. Ask the developer for the design before inventing mechanics.

### rm10. Web release build (priority 10)

Goal: build each game for the browser and host it. Both macOS and Web must keep working (`CLAUDE.md`, "Targets and scope"). Done: the `wasm32-unknown-unknown` target is pinned (`adr-e5`), `./dev-scripts/rust.sh web` checks that the games compile for it, and `[profile.wasm-release]` in the root `Cargo.toml` is set for small builds (`adr-e6`). Not done: producing the files, running them in a browser (no game has been run in one yet) and hosting.

Considerations: the tool that turns the `.wasm` into a page (`wasm-bindgen` CLI, Trunk or another), to be checked for the pinned Bevy and Rust versions; the HTML shell and canvas sizing with the fixed-height camera (`adr-e7`); asset loading over HTTP, so a loading state keeps the web build from showing missing assets (`bevy_asset_loader` style, `CLAUDE.md`), and `.aseprite` files loaded through `bevy_aseprite_ultra` must work there; the F1 map reload and the scripted run tool are native only, so the bundled `include_str!` maps are what the web build uses (`rm3`); `wasm-opt` and the size of the download; one build per game; hosting (for example GitHub Pages for the repository `wernerpyke/bevy-games`); keeping `dev-docs/` out of the shipped files; and how to test (a script that builds, serves and opens the page, using `dev-scripts/shot.sh` and `dev-scripts/aseprite.sh`). Record the chosen method in `dev-docs/adr/ENGINE.md` and replace the "to define" lines in `CLAUDE.md` and `adr-e6`.

### rm11. Rethink marker collision and touch areas (priority 11)

Goal: decide whether a marker needs two rectangles. Now a marker has a blocked area (the middle 80% of its width and the bottom half of its height, `adr-lw20`) and, when it has `exit_to`, a touch area: the blocked area plus `TOUCH_MARGIN` (2 px), scaled by `TOUCH_SCALE` (2.0) around its centre, 52 by 44 px (`markers.rs`, `adr-lw20`, `adr-lw21`, `adr-x33`). Considerations: one larger blocked area may be simpler, because the player would reach the exit by touching the edge of the box and the margin and the scale would go away. The cost is a larger solid box that blocks more ground and changes how markers merge into clusters with trees and rocks. Compare by playing. Questions: whether lanterns, which have no exit, keep the small box; whether the arrival at `player_start` next to a marker still works with a larger box (the `armed` rule, `adr-x33`); and whether the debug overlay should draw the touch area. Not decided: the two area design stays until this is looked at.

### rm12. Screens and the overlay HUD (priority 12)

Goal: use the screen layout and app states (`adr-x34`, `adr-x35`) for real screens, and the HUD over the game. Long Way now has its HUD bar below the game and a weapon drawer over the game area (`adr-lw31`). Done in the kit: regions, the HUD bar, `AppState` with loading, title, playing and game over, pause with a dim layer and an empty `PauseDialog`. Not done: content for any screen. Long Way starts in `Playing`, has no pause key and no title, pause dialog or game over screen.

Considerations: ask the user what each screen shows before inventing it; the title and game over screens use the full window on their own background (`state_root`), and the title may need the game camera off or a world behind it; a death and restart flow (`rm9`) needs `GameOver` and a reset of the game; the pause dialog is in the game region and may need a full-window position; the HUD needs real content (health, items) and icon and gauge widgets; the overlay mode (the HUD over a full-window game view, same content) is computed and tested but not used, and its transparent root and picking need a try; kit systems are not gated by state, so a game must not spawn the player in the title; a `ViewportNode` spike if one UI tree for all modes is wanted (not checked on wasm); mouse to world must use the game viewport when the mouse is added (`rm8`).

### rm13. Adapt to the screen size and ratio (priority 13)

Goal: the kit and the games know the size and shape of the screen they run on and adjust the window and layout, instead of using one fixed window size. Today Long Way has a fixed window of 576 by 756 (`camera.rs`); the game width follows the window aspect ratio (a wider window shows more world), the HUD bar is always the full window width, and nothing checks that the window fits the monitor. Builds on `rm12` (`ScreenLayout` and `UiScale` already follow the window size).

Considerations: read the monitor size and pick a window that fits (a 720 by 945 window did not fit this Mac: macOS shrank it and the view grew wider than 8 cells); fullscreen and free resize; what a very wide or very tall window does (show more world, letterbox, or limit the aspect ratio, and what the camera bounds and map edges then show); the integer scaling rule in `CLAUDE.md`, which the scale of 1.40625 already breaks (choose a whole number scale of the art, or accept a fractional one and say so); the web canvas size and the browser window (`rm10`); whether the HUD size is a fixed share of the view or adapts to the window shape, for example a phone-shaped window; high-DPI screens (scale factor 2 on this Mac); and tests for the layout function with many window shapes. Ask the user for the target screens (desktop only, or also phones and tablets on the web) before deciding.

### rm14. Repeating pattern backgrounds (priority 14)

The `background:` block already has a mandatory `mode`, and `pattern` is reserved (`adr-x36`): the parser rejects it as not implemented. Build it: how a pattern is written in the map file (a short repeat of image names, or a tile image per cell row), how it combines with `jitter` and `scale`, and whether R-Town uses it for a tiled ground (`rm5`). Ask the user what a pattern should look like before inventing the format.

### rm90. Further disk savings for `target/` (priority 90)

`target/` is 2.9 GB after a clean build of all games and 4.3 GB with `lint`, `test` and `web` (5.2 GB after the first `run`; it was 25 GB before debug info was removed and 13 GB with stale and duplicate builds, `adr-e8`). `cargo-sweep` is still not installed. Only look at more savings if `target/` grows past the limit in `CLAUDE.md` ("Disk use") even with the routine. Options, each to be measured before it is kept: `split-debuginfo = "unpacked"` for `[profile.dev]` (macOS only), no incremental builds for dependencies, one shared `CARGO_TARGET_DIR` for all projects (saves space when they share a Bevy version, but all builds lock one folder), and `cargo-sweep` (`cargo install cargo-sweep`, then test that `--time` removes the right files on macOS; `rust.sh prune` already runs it when installed). Install `cargo-sweep` earlier if the project starts to use several Bevy versions or toolchains, or a shared target folder. Do not make `bevy/dynamic_linking` a default: it makes a second full set of outputs. Known learning: each game binary stays about 140 MB because Bevy is built at `opt-level = 3`. The savings came from `target/debug/deps`.
