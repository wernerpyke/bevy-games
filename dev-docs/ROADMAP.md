# Roadmap

## Items for Future Implementation

### 1. Art pipeline

Finish the art pipeline for Long Way. Done: the palette is chosen and grows by appending colours (`adr-a4`, `adr-a5`, 32 colours); the map cell is 64 px and art is drawn at 1x or at a whole-number scale; the player is the Hunter, built from a sprite pack with `tagged_sheets.lua`, `extend_palette.lua` and `resize.lua` (`adr-lw15`, `games/long-way/docs/HUNTER-sprites.md`). Existing assets in `~/Dark/graveyard_shift/diodrama-assets/` are still copied one file at a time on request (`adr-a3`). `Guy.aseprite` is still in `assets/art/characters/` but no code uses it.

Remaining: decide whether the sprite sizes need one grid rule (now: Hunter 128x128 at 1x, trees 128x128, rocks 32x32 at 4x); write the shared helper `dev-scripts/aseprite/lib.lua` from `art-pipeline.md` rule 1 (not written, the scripts are standalone); draw real `Up` and `Down` walk frames and an idle for each direction (placeholders from the pack jump frames now); decide whether to draw or drop the `Block` tag; wire up the `Hurt` and `Die` tags (no code plays them); and, when attacks come, add the attack, charge, special and dash sheets and split the baked-in effects into separate sprites. Decide whether to delete `Guy.aseprite`.

### 2. Evaluate avian2d

Spike `avian2d` 0.8.0 (declares `bevy ^0.20`) in a separate game under `games/` and compare it with the custom collision in `adr-lw1`. Questions to answer: whether the 50% overlap from below and the walk-behind-from-above rules can be expressed with sensors or collision filters, wasm build size and build time against the current baseline, behaviour with real-time top-down movement and later NPCs (`adr-lw7`), and how testable the result is without a running world. Check that it compiles for `wasm32-unknown-unknown`. Record the outcome as a decision in `dev-docs/adr/`. `bevy_rapier2d` 0.37.0 also declares Bevy 0.20 and can be included in the comparison. Not compiled yet.

### 3. Robust map and collision pipeline

R-Town and Long Way reload their map from disk on F1 on native (`adr-rt8`, the key is in the kit, `reload.rs`); the web build does not. The kit now has an occupancy grid and A* path finding built from the collision outlines (`adr-x23`), which covers the first part of the navigation idea below. The maps use `include_str!` and an own parser for the front matter and the drawn grid (`adr-lw8`, `adr-x18`). For a real-time RPG with many areas, plan a sturdier approach. Considerations: a Bevy asset loader with hot reload (edit a map and see it without a rebuild, also on the web build); a real YAML parser or Tiled maps (`bevy_ecs_tiled`) instead of the own subset; validation with clear errors; one map file per area with chunked collision; dynamic obstacles (doors, destroyed objects) that rebuild one cluster; a broad phase for many moving entities; and a navigation mesh or occupancy grid for NPC pathfinding built from the same outline. Decide when the second map or the first NPC appears.

### 4. Map data beyond one grid

Maps are text files with front matter and one drawn grid, one character per cell (`dev-docs/extensions/map-files.md`, `games/long-way/docs/maps.md`, `adr-x18`, research in `dev-docs/RESEARCH-map-layouts.md`). This suits maps that a human reads and edits as a picture. Maps may become more complex than one object per cell handles well: several layers (ground and objects), objects with their own settings, areas with triggers or dialogue, enemies and paths, and values that need real types (numbers, lists, nested data). Options: more grids in the same file (a `layer:` name per grid), a companion YAML or TOML file for data, chunk files for large maps, and generated maps (a seeded generator, with a per-chunk seed from the master seed and the chunk position, can return the same `Map` as the parser). Questions to answer: how layers and larger objects look in the grid, whether the human editing experience stays as good, error messages with line numbers, wasm support of any parser crate (check each crate for the pinned Rust and Bevy), and how it fits with roadmap item 3 (asset loader, hot reload, Tiled maps). Not worth doing now. Decide when a map needs data that one grid handles badly. Keep the parser in `map.rs` behind one function (`parse`) so the format can change without touching the code that spawns objects. Update 2026-11-06: the front matter now has two more nested blocks, `exits:` and `entries:` (`adr-x30`), read by the same parser. They show the pattern for map data that is not one object per cell. Moving between maps is planned in `dev-docs/PLAN-map-transitions.md`.

### 5. Tiled backgrounds

Give maps a ground made of tiles, so R-Town can draw grass, paths, stone and water instead of one flat colour (the placeholder `GROUND_COLOR` in `games/r-town/src/map.rs`). The pack's `0-tileset.png` (320x192, a 16 px grid of 20x12 tiles) is the first source. Considerations: how a map file describes a tile layer (a new section in the markdown format, or an external editor format such as Tiled, which ties in with item 6); whether a maintained crate fits the pinned Bevy version and wasm (for example `bevy_ecs_tilemap`, to be checked before any decision) or custom code, with the chunked drawing that a 60x60 map needs; where tiles sit in the draw order (`BACKGROUND_Z` and its sublayers in the kit layers); how blocking tiles such as water feed `CollisionWorld` (`adr-rt5`: water blocks the player), merged into the same clusters as objects; packing the terrain tiles into an `.aseprite` file with tags (`adr-rt1`, `adr-rt6`); and whether the kit or the game owns the tile layer.

### 6. Visual map editor

Goal: edit a map by clicking cells and save the result in the text map format (`dev-docs/extensions/map-files.md`, `adr-x18`). The text file stays the source of truth, so editing by hand keeps working. Build it later, after the map format settles (items 3 and 4).

Considerations. The editor reads and writes the same files as the game, and a round trip must not change a file the user did not edit. It keeps comments, rulers, row labels, blank footprint cells and the front matter as written. The parser in `game-kit` (`parse`) does not keep these, so the editor needs a writer that edits the text in place, or a parser that returns the layout with the objects. Options: an in-game editor on top of the F3 grid and the debug tools (Bevy, native and web, no new language, and it draws the real art and footprints); or a separate tool. The language rule applies: Rust, Lua and shell only, and any other language needs approval. Features to consider: pick a kind from the legend and paint or erase cells, undo, a live footprint outline, the player start marker, a size change that adds or removes rows and columns, errors from `parse` shown in the editor, and a save that keeps `origin` (`bottom-left` or `top-left`) and the row labels right. Research on existing editors (Tiled, LDtk, Ogmo and the plain text editors for ASCII maps) is in `dev-docs/RESEARCH-map-layouts.md`. Those need their own UI and formats, so they are not a fit for now.

Known issues. The file has no footprint data, so the editor needs the sizes from the game (`Kind` and its art) to draw footprints. Layers and objects bigger than one cell were left out of the format on purpose, and an editor may bring them back (item 4). Seeded generated maps (item 4) would need a way to save a generated result and then edit it as a normal map.

### 7. Re-assess the group footprint rule

An item that stands alone blocks a thin band and a member of a group blocks its whole footprint (`adr-x20`, `adr-rt9`, `adr-lw14`). Check by playing whether this feels right and whether the area per member should change. Considerations: a thinner footprint for tall trees so the player can walk closer behind a grove; a footprint per kind; corner contact linking items (8 neighbours) so that a single diagonal neighbour turns a passable tree into a solid one; a deliberate gap size; and the Long Way top inset that is dropped when a member sits above (`Group::neighbour_above`). Known issue: a lone rock in Long Way now has a 12.8 px band, which the developer has not yet tried in play.

### 8. Keyboard and mouse input in the game-kit

Input handling starts as a game-local module in R-Town: a `PlayerInput` resource (move direction, fire) filled from the keyboard, read by the player and weapon code (`adr-x22`). Move it to the kit when the mouse is added or a second game needs it. Considerations: one resource that games read, so no game code reads `KeyCode` or mouse buttons directly; keyboard and mouse as two sources that write the same resource, with the last used device winning; mouse aim converted from window position to world position through the pixel camera (integer scaling and the letterbox), and an aim direction that can replace the facing direction; named actions with default key bindings that a game can override, and later rebinding and gamepads; the scripted run tool (`script.rs`) must keep working by writing key presses into `ButtonInput`, and may need a way to place the mouse; wasm differences (pointer lock, touch). Keep game specific actions out of the kit, as for the other modules (`adr-x12`).

### 9. Combat basics

Projectiles and enemies exist (`### Enemies (R-Town)` under completed items), but there are no hit points. Considerations: hit points and damage, an impact effect and sound, a death screen and a restart flow with a game state (`States`), enemy attacks, weapon values in one place (speed, cooldown, range, damage) and more than one weapon, and exact blocked shapes for projectiles if the 5 px early stop at tree sides is a problem (`adr-x21`). Decide when the first enemy is designed. Ask the developer for the design before inventing mechanics.

### 10. Web release build

Goal: build each game for the browser and host it. Both macOS and Web must keep working (`CLAUDE.md`, "Targets and scope"). Done: the `wasm32-unknown-unknown` target is pinned (`adr-e5`), `./dev-scripts/rust.sh web` checks that the games compile for it, and `[profile.wasm-release]` in the root `Cargo.toml` is set for small builds (`adr-e6`). Not done: producing the files, running them in a browser (no game has been run in one yet) and hosting.

Considerations: the tool that turns the `.wasm` into a page (`wasm-bindgen` CLI, Trunk or another), to be checked for the pinned Bevy and Rust versions; the HTML shell and canvas sizing with the fixed-height camera (`adr-e7`); asset loading over HTTP, so a loading state keeps the web build from showing missing assets (`bevy_asset_loader` style, `CLAUDE.md`), and `.aseprite` files loaded through `bevy_aseprite_ultra` must work there; the F1 map reload and the scripted run tool are native only, so the bundled `include_str!` maps are what the web build uses (item 3); `wasm-opt` and the size of the download; one build per game; hosting (for example GitHub Pages for the repository `wernerpyke/bevy-games`); keeping `dev-docs/` out of the shipped files; and how to test (a script that builds, serves and opens the page, using `dev-scripts/shot.sh` and `dev-scripts/aseprite.sh`). Record the chosen method in `dev-docs/adr/ENGINE.md` and replace the "to define" lines in `CLAUDE.md` and `adr-e6`.

### 11. Nav paths that start at a box corner

Goal: a path leg must not cut through a blocked area. In a kit nav test with box corners on nav grid points, the original code gave a leg from a box corner straight through the box, because `segment_blocked` passes a line that starts exactly on a convex corner. R-Town has 16 px cells and a nav step of 4, so box corners are on grid points there. Known issues and learnings: not reproduced in the R-Town game yet. Check with a scripted run, then make `segment_blocked` stop a segment that starts on a corner and heads into the shape.

### 90. Further disk savings for `target/` (low priority)

`target/` is 2.2 GB after a clean build and 3.2 GB with `lint`, `test` and `web` (it was 25 GB before debug info was removed, `adr-e8`). Only look at more savings if `target/` grows past the limit in `CLAUDE.md` ("Disk use") even with the routine. Options, each to be measured before it is kept: `split-debuginfo = "unpacked"` for `[profile.dev]` (macOS only), no incremental builds for dependencies, one shared `CARGO_TARGET_DIR` for all projects (saves space when they share a Bevy version, but all builds lock one folder), and `cargo-sweep` (`cargo install cargo-sweep`, then test that `--time` removes the right files on macOS; `rust.sh prune` already runs it when installed). Install `cargo-sweep` earlier if the project starts to use several Bevy versions or toolchains, or a shared target folder. Do not make `bevy/dynamic_linking` a default: it makes a second full set of outputs. Known learning: each game binary stays about 140 MB because Bevy is built at `opt-level = 3`. The savings came from `target/debug/deps`.

### 99. Debug grid: overlapping corner labels (low priority, cosmetic)

With the grid origin at the bottom left, the column "0" label (top edge) and the highest row label (left edge) overlap in the top left corner. Found in a screenshot on 2026-11-01. This is cosmetic and has low priority. Fix by moving the row labels, for example to the bottom of each cell, or by hiding the row label that sits on the top edge. The info box also covers the top left row labels, but F2 and F3 toggle each tool, so that needs no fix.

## Completed Items

### Reusable dev-scripts for screenshots and art checks

Done 2026-11-05. `dev-scripts/shot.sh <game> <name> "<commands>" cx= cy= w= h= scale=` runs a scripted run with `--debug`, takes the screenshot and saves a zoomed crop in world units (`target/screenshots/<name>_crop.png`). `dev-scripts/aseprite.sh <script> <file> key=value ...` runs one of four Lua scripts in `dev-scripts/aseprite/`: `crop` (screen or world region, nearest scale), `frame_grid` (a tag or frame range as one scaled grid PNG), `check` (canvas, colour mode, layers, tags with frames and durations, palette check against `diodrama_palette.aseprite`, bounds and feet row per frame, frames cut off at the edge) and `sheet_analysis` (per frame bounds and colours of a pack sheet). The crop is done in Lua and not in `script.rs`, so the kit has no new dependency. Known issues: the crop is centred on world coordinates you give, not on the player automatically; `shot.sh` reads `VIEW_HEIGHT` from `games/<game>/src/camera.rs` with a regex; `lib.lua` (art pipeline rule 1) is still not written, so the scripts stay standalone. Usage: `dev-docs/extensions/dev-scripts.md`.

### Enemies (R-Town)

Done 2026-11-04. A skeleton (random patrol within 120 px) and a goblin (pursues the player) spawn from legend entries of `test.txt` (`every=` and `strategy=` parameters), walk around trees and water with grid path finding, die when a projectile hits them, and kill the player on a touch. F1 resets the whole game state. The kit has the nav grid, goal movement, strategies, spawners, hit boxes, a seedable random number generator and a movement debug view (`dev-docs/extensions/nav.md`, `enemy-movement.md`, `spawners.md`, `adr-x23` to `adr-x27`, `adr-rt12`, `adr-rt13`). Known issues and follow-ups: the screens were not seen by Claude (the display was black during the scripted runs), no hit points or death screen, enemies may overlap, no check that a spawner stands on free ground, no rule against spawning next to the player, a fixed spawn interval only, and the sprites are one front view each.

### Projectile weapons (R-Town)

Done 2026-11-04. X fires a projectile along the player's facing at twice the walk speed. It disappears at blocked areas and the map edge (`dev-docs/extensions/projectiles.md`, `adr-x21`, `adr-rt11`). The flight, hit message and sprite turning are in `game-kit`. Input went through a game-local `PlayerInput` resource (`adr-x22`, roadmap item 8). Known issues and follow-ups: no damage or hit effects yet (nothing reads `ProjectileHit`), no cooldown or range, a shot stops up to 5 px before the side of a tree because it uses the player's collision areas.

### Text map files

Done 2026-11-02. A map is one text file with front matter and a drawn grid that shows every cell (`dev-docs/extensions/map-files.md`, `adr-x18`, `adr-lw8`, `adr-rt7`). The parser in `game-kit` reads blanks and `.` as empty, checks row labels, rulers and sizes, supports `origin: bottom-left` and `top-left`, and treats legend markers such as `player_start` as ordinary objects. Long Way (`rocks-test.txt`, 32x18) and R-Town (`test.txt`, 60x60, top-left) load their maps this way. The F3 grid can number rows from the top to match a top-left file. Research on other formats and on seeded generation is in `dev-docs/RESEARCH-map-layouts.md`. Known issues and follow-ups: no layers and one object per cell (roadmap item 4), footprint drawings are not checked against the real sizes, and the maps are bundled with `include_str!`, with a reload from disk on native (item 3).

### Shared code in the game-kit crate

Done 2026-11-02. A second game, R-Town, needed the code of Long Way, so the shared crate `crates/game-kit` was created (`adr-w6`, `adr-x12`). It holds the collision engine with merged outlines and sliding (`Blocker`, `SlideTuning`, `adr-x16`), the depth sort and default layers (`adr-x14`), the markdown map parser with string kinds (`adr-x13`), the pixel camera with a follow system (`adr-x17`), the debug grid, info box and collision overlay, and the scripted run tool (`adr-x15`). Games pass their values through plugin fields and the `Controlled` marker, with no generics. Long Way keeps `Trunk`, the player constants, its kinds and its art. The tests moved with the code, and the kit builds and tests on its own. Learnings: build and test the kit alone, because a workspace build unifies Bevy features and hid a missing `ui_api` feature. Debug sizes must scale with the cell size. Known issues and follow-ups: the scripted run tool has no way to register game specific commands yet (`adr-x15`), the kit has no camera shake or smoothing, and the scrolling debug grid was checked in R-Town only.

### Tune sliding by playing

Done 2026-11-02. The developer played with rocks and trees and accepted the slide rules as they are (`adr-x10`). ### Tree collision

Done 2026-10-31. The player cannot overlap a trunk from the left or right, can overlap it by 50% of its height when walking up from below, and can walk behind the tree from above but not into its bottom 10%. Draw order follows the feet so it passes behind and in front correctly. The rules are in `games/long-way/src/collision.rs` with 8 unit tests that pass. The blocked areas were first shown with F1 (now the F3 overlay). See `games/long-way/docs/adr.md`. Not tested by hand: the real feel at the screen edge, whether the debug gizmos draw on top of sprites, and the trunk edges (taken from art pixels) and the player's body width (20 each side, an estimate) on screen. Since then: the 50% overlap from below was replaced by a stop at the base line (2026-11-02, `adr-lw1`) and the half width is 14 (`adr-lw15`).

### Forgiving collision (`allow_sliding`)

Done 2026-10-31. `CollisionPlugin { allow_sliding }` is set to `true` for Long Way. Walking straight into a trunk stops the player. After 0.2 seconds of pushing (first 0.5, shortened after the developer tried it), if it is near an edge of the face (within 35% of its length), it slides past it and carries on. The middle of a face never slides it. With the flag off, any blocked move stops it completely. Fixed 2026-10-31 after the developer found it did not work: the push timer reset every few frames because directions were compared as floats (`adr-x5`). Verified in the real game with scripted input: from feet x = 225 the player stops at the trunk, slides left after the delay and walks on; from x = 240 (too far from an edge) it stays stopped. 16 unit tests pass. Tuning constants (`SLIDE_DELAY`, `SLIDE_SPEED`, `SLIDE_RANGE_FRACTION`) were guesses at the time and were tuned by playing later (see "Tune sliding by playing"). See `adr-x4`.
